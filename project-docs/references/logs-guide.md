# Logs Guide — извлечение и классификация log-вызовов

Гайд для фазы 3. Цель — карта логов для `TESTING.md`: тестировщик по строке в логе должен понимать, какой шаг отработал и успешен ли прогон.

## 1. Паттерны поиска log-вызовов

| Стек | Паттерны для `rg` |
|---|---|
| Python (logging) | `log(ger)?\.(debug\|info\|warning\|error\|exception\|critical)\(` |
| Python (structlog) | `\.(debug\|info\|warning\|error\|exception)\(` с `structlog` в импортах |
| Python (loguru) | `logger\.(debug\|info\|warning\|error\|exception)\(` |
| Java/Kotlin (slf4j) | `log\.(debug\|info\|warn\|error)\(` |
| Go (slog) | `slog\.(Debug\|Info\|Warn\|Error)\(` |
| Go (zap/logrus) | `\.(Info\|Warn\|Error\|Fatal)\(` с `zap`/`logrus` в импортах |
| JS/TS | `console\.(log\|info\|warn\|error)\(`, `logger\.(info\|warn\|error)\(` (pino/winston) |

Команда-заготовка (подставь паттерн стека):

```bash
rg -n --no-heading '<PATTERN>' --type <LANG> <PROJECT_ROOT>/src
```

## 2. Отбор значимых вызовов

Не все log-вызовы попадают в карту. Брать только те, что отмечают наблюдаемые вехи:

- старт/завершение операции или шага пайплайна;
- успешное завершение всей обработки (финальный успех);
- обращение к внешней системе и его результат;
- ошибки и отказы;
- бизнес-события (отправка сообщения в очередь, смена статуса в БД).

Не брать: debug-шум внутри циклов, технические логи фреймворка, дублирующие сообщения.

## 3. Классификация

| Класс | Признак | Для тестировщика |
|---|---|---|
| `START` | «запуск», «получен запрос», «start process» | Обработка началась |
| `SUCCESS_STEP` | завершение промежуточного шага | Шаг N отработал |
| `SUCCESS_FINAL` | «завершено», «отправлено в Kafka», «finalized» | Весь прогон успешен |
| `WARNING` | `warning/warn`, нестандартные, но обработанные ситуации | Не баг, но зафиксировать |
| `ERROR` | `error/exception/critical`, `failed` | Сбой; смотреть трактовку в разделе ошибок |
| `AUDIT` | смена статуса, запись результата | Проверка соответствия БД и логов |

## 4. Построение grep-паттерна

Паттерн для тестировщика = **стабильная константная часть** сообщения:

- f-строки и форматирование: отрезай интерполируемые переменные. `logger.info(f"Документ {doc_id} классифицирован")` → паттерн `Документ .* классифицирован` или, если система логов не поддерживает regex, `классифицирован`.
- Многоязычные сообщения: бери самый устойчивый фрагмент (без склонений, которые могут измениться).
- Структурные логи (structlog/json): паттерн = имя события, например `"event": "document_classified"`. Именно его давать в таблицу.
- Если сообщение собирается из переменной целиком (`logger.info(msg)`) — такой вызов в карту не включать: паттерн непредсказуем.

## 5. Формат строки карты

Для каждого события зафиксируй (колонки таблицы в `TESTING.md`):

| Поле | Откуда |
|---|---|
| Шаг пайплайна | привязка к шагу из ARCHITECTURE.md (нумерация сквозная) |
| Паттерн для поиска | стабильный фрагмент сообщения (см. п. 4) |
| Уровень | info / warning / error из кода |
| Где в коде | `файл:строка` — для проверки и актуализации |
| Что означает | одна фраза: что уже произошло к этому моменту |

## 6. Обязательные элементы карты

1. **Сквозной идентификатор.** Найди в коде trace/request/correlation id (`trace_id`, `rq_uid`, `request_id`, middleware с request-id). Первая строка карты — «как получить/найти id прогона», далее в пояснении: фильтровать логи по нему, чтобы видеть один прогон целиком.
2. **Финальный успех.** В карте обязана быть строка, по которой однозначно понятно «всё завершилось успешно» (финализация, отправка результата). Если в коде такого лога нет — это пробел: зафиксируй его в отчёте пользователю и в `TESTING.md` предложи ближайший доступный маркер (например, статус в БД) с явной пометкой «явного лога успеха нет».
3. **Порядок.** Строки карты — в хронологическом порядке шагов, а не в порядке нахождения в коде.

## 7. Валидация

Для каждого паттерна в итоговой карте выполни проверку:

```bash
rg -n '<PATTERN>' <PROJECT_ROOT>
```

Паттерн обязан находить хотя бы одну строку в исходном коде. Не нашёлся — исправь или удали строку карты. Эта проверка входит в self-review чеклист SKILL.md.
