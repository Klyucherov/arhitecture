# Project Docs — генератор документации по проекту

Скилл обследует кодовую базу и создаёт в корне анализируемого проекта три документа:

| Файл | Аудитория | Содержание |
|---|---|---|
| `ARCHITECTURE.md` | Разработчики, аналитики | Назначение, стек, mermaid-диаграммы, структура проекта, API, модель данных, пайплайны, обработка ошибок, интеграции |
| `TESTING.md` | Тестировщики | Что делает сервис простым языком, сценарии проверки, карта успешных логов с grep-паттернами, трактовка ошибок |
| `AGENTS.md` | LLM-агенты | Компактный (≤150 строк) ориентир: команды, границы, неочевидные решения, ссылки на два больших документа |

## Жёсткие правила

1. **Только факты из кода.** Каждое утверждение подтверждено источником (файл, роут, таблица, log-вызов). Раздел, который не удалось подтвердить, — пропустить, а не выдумывать. Запрещены «вероятно», «скорее всего» в описании фактов.
2. **Русский язык** во всех трёх документах. Идентификаторы, команды, сообщения логов и названия технологий оставлять в оригинале.
3. **Безопасность закрытого контура.** Не копировать в документы секреты, пароли, токены, приватные ключи, реальные внутренние хосты и IP-адреса. В примерах заменять на описание в угловых скобках: `<host Kafka>`.
4. **Mermaid без стилей.** Никаких `style`, `classDef`, `click`, цветов. ID узлов — без пробелов. Подписи со скобками, запятыми, двоеточиями — в двойных кавычках. Зарезервированные слова (`end`, `graph`, `subgraph`) не использовать как ID. Подробности — в [references/style-guide.md](references/style-guide.md).
5. **Существующие файлы не затирать молча.** Если `ARCHITECTURE.md` / `TESTING.md` / `AGENTS.md` уже есть — прочитать, обновить по фактам, сохранив ручные правки и структуру, где она осмысленна. При радикальных расхождениях — спросить пользователя.
6. **Дата и версия в шапке** каждого сгенерированного файла.

## Режимы работы

Скилл работает в трёх режимах. Режим определяй из формулировки пользователя; если не указан — используй `full`.

| Режим | Триггеры пользователя | Что делать |
|---|---|---|
| `full` | «задокументируй проект», «сгенерируй документацию», режим не указан | Полный цикл фаз 0–6, генерация всех трёх файлов |
| `update` | «обнови документацию», «актуализируй ARCHITECTURE.md», «доки устарели» | Прочитай существующие документы, сверь каждый раздел с кодом, точечно обнови устаревшее. Ручные правки и структуру сохраняй; не переписывай разделы, по которым в коде ничего не изменилось. Если в шапке есть дата — обнови её |
| `check` | «проверь документацию», «документы актуальны?» | Read-only: ничего не переписывай. Запусти `validate_docs.py` + spot-check 3–5 фактов из документов grep-ом, выдай отчёт о расхождениях списком «раздел → факт → что в коде сейчас» |

Режимы `update` и `check` запускаются только по явной просьбе пользователя — никакой автоматики по коммитам или расписанию.

## Workflow

### Фаза 0. Подготовка

- Определи корень анализируемого проекта (по умолчанию — текущая рабочая директория).
- Проверь наличие существующих `ARCHITECTURE.md`, `TESTING.md`, `AGENTS.md`, `README*` — прочитай их до начала анализа.

### Фаза 1. Recon — быстрый обзор

Запусти детерминированный сборщик фактов из директории этого скилла (`<SKILL_DIR>` — директория, где лежит данный `SKILL.md`, обычно `~/.gigacode/skills/project-docs`):

```bash
python3 <SKILL_DIR>/scripts/scan_project.py <PROJECT_ROOT>
```

Скрипт использует только Python stdlib и работает в закрытом контуре. Он возвращает JSON: дерево проекта, детектированный стек, манифесты, точки входа, миграции, существующие доки, статистику log-вызовов.

Если `python3` недоступен — собери те же факты вручную: glob по манифестам и `README*`, дерево через list/glob с исключением `node_modules`, `.git`, `.venv`, `dist`, `build`, `target`.

Затем прочитай ключевые файлы верхнего уровня:

- манифесты зависимостей (`pyproject.toml`, `requirements.txt`, `pom.xml`, `build.gradle*`, `go.mod`, `package.json`, `Cargo.toml`);
- конфигурацию (`config.py`, `settings.*`, `application.yml`, `.env.example`, `config.yaml`);
- `Dockerfile`, `docker-compose*.yml`, `Makefile` — оттуда бери команды запуска, порты, внешние зависимости;
- каталог миграций (`alembic/`, `migrations/`, `flyway/`) — источник правды о схеме БД.

### Фаза 2. Deep dive по доменам

Следуй карте поисковых паттернов из [references/discovery.md](references/discovery.md). Собери по каждому домену, который реально присутствует в проекте:

- **Точки входа и жизненный цикл** — что происходит при старте и остановке (lifespan, main, init).
- **HTTP API** — полная таблица endpoints: метод, путь, назначение, источник в коде.
- **Очереди сообщений** — топики/очереди, producers, consumers, форматы сообщений.
- **База данных** — таблицы/модели, связи, enum-статусы, миграции.
- **Внешние интеграции** — HTTP/gRPC-клиенты к другим системам, объектные хранилища, почта; для каждой: направление (исходящая/входящая), протокол, назначение.
- **Фоновые задачи** — watchdog-и, scheduler-ы, cron, периодические asyncio-задачи.
- **Конфигурация** — env-переменные и их смысл.
- **Примеры запросов и ответов** — для каждой точки входа (HTTP endpoint, сообщение очереди) собери реальные примеры: тело запроса, успешный ответ, ошибочные ответы. Источники — модели запросов/ответов, тесты, фикстуры, openapi-спеки (см. [references/discovery.md](references/discovery.md), раздел 11). Ничего не выдумывай: пример, которого нет в коде, в документ не попадает.
- **Контракты** — каталог `contracts/` (если есть): источник истины по входным/выходным контрактам, ведётся аналитиком через PR. Перечисли интерфейсы (файл, вид, направление, версия из frontmatter) в разделе «Контракты» ARCHITECTURE.md и свяжи каждый с реализацией в коде. Расхождение контракта с кодом — отметь в отчёте, код не править (это задача скилла `contract-sync`).

**Большие проекты** (>300 файлов кода или несколько слабо связанных доменов): делегируй исследование субагентам GigaCode параллельно — по одному read-only субагенту на домен (`api`, `db`, `integrations`, `background`), затем сведи результаты. Пример формулировки: «Исследуй только HTTP API проекта: найди все роуты, верни таблицу метод/путь/файл:строка/назначение. Файлы не изменяй».

### Фаза 3. Карта логов (ядро TESTING.md)

Следуй [references/logs-guide.md](references/logs-guide.md):

1. Извлеки реальные log-вызовы из кода grep-паттернами под детектированный стек.
2. Классифицируй каждый вызов: `START` / `SUCCESS_STEP` / `SUCCESS_FINAL` / `WARNING` / `ERROR` / `AUDIT`.
3. Для каждого вызова построй стабильный grep-паттерн (константный префикс сообщения без интерполируемых переменных).
4. Привяжи логи к шагам пайплайна — тестировщик должен понимать: «вижу эту строку в логе → этот шаг отработал успешно».

### Фаза 4. Генерация файлов

Заполни три шаблона фактами и запиши в корень анализируемого проекта:

| Шаблон | Результат |
|---|---|
| [templates/ARCHITECTURE.template.md](templates/ARCHITECTURE.template.md) | `<PROJECT_ROOT>/ARCHITECTURE.md` |
| [templates/TESTING.template.md](templates/TESTING.template.md) | `<PROJECT_ROOT>/TESTING.md` |
| [templates/AGENTS.template.md](templates/AGENTS.template.md) | `<PROJECT_ROOT>/AGENTS.md` |

Правила заполнения:

- Удали все HTML-комментарии-инструкции (`<!-- ... -->`) из результата.
- Удали разделы, которые не подтвердились фактами (не оставляй пустые таблицы и «TODO»).
- Актуализируй «Содержание» после удаления разделов.
- Проставь дату генерации и версию сервиса (из манифеста или тега; если неизвестна — `не указана`).
- Пиши в стиле [references/style-guide.md](references/style-guide.md).

### Фаза 5. Self-review — обязательный чеклист

Сначала запусти детерминированный валидатор и исправь всё, что он найдёт:

```bash
python3 <SKILL_DIR>/scripts/validate_docs.py <PROJECT_ROOT>
```

Затем пройди по ручному чеклисту:

- [ ] Каждый раздел заполнен фактами; нет пустых таблиц, `TODO`, `???`, комментариев-инструкций.
- [ ] Spot-check: 3–5 случайных endpoints/таблиц/топиков из документов находятся в коде через grep.
- [ ] Каждый grep-паттерн из карты логов `TESTING.md` реально находит строку в коде (валидатор проверяет это, но перепроверь подозрительные вручную).
- [ ] Примеры запросов и ответов в `TESTING.md` взяты из кода/тестов/спек, а не сгенерированы «по смыслу».
- [ ] Mermaid-диаграммы синтаксически валидны: нет `style`/`classDef`/`click`, ID без пробелов, подписи со спецсимволами в кавычках.
- [ ] `AGENTS.md` не длиннее 150 строк.
- [ ] В документах нет секретов, паролей, внутренних хостов и IP-адресов.
- [ ] Даты, версии и «Содержание» соответствуют итоговой структуре.
- [ ] Терминология едина во всех трёх файлах (один термин — одно слово).

### Фаза 6. Отчёт пользователю

Дай краткую сводку:

- какие файлы созданы/обновлены;
- покрытие в цифрах: сколько endpoints, таблиц БД, топиков, интеграций, log-событий задокументировано;
- пробелы: модули, которые не удалось понять или подтвердить (мёртвый код, неочевидная логика) — отдельным списком;
- рекомендация: что перепроверить вручную.
